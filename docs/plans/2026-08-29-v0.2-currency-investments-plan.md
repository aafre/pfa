## B-1 - Barclaycard uses a two-column magazine layout

Probed with `pdfplumber`: 4 pages, digital text (no OCR needed), ~300-930 words per page.
Transactions sit in the **left column of page 2**, and `extract_text()` interleaves them
line by line with marketing copy from the right column:

```text
27 <date> <merchant>, London       GBP <amt>
Understanding your interest            <- right column bleeding in
27 <date> <merchant>, London       GBP <amt>
Your interest rates: ...               <- right column again
```

There is no conventional `Date | Description | Amount` header anywhere on the page, and
the pound sign decodes as a replacement character.

This is a **reading-order** problem, not the header/date/sign problem HSBC and AMEX have.
It needs x-position clustering into columns before lines are assembled. The extractor
already works on positioned `Word` objects, so the raw material is there. Treat it as its
own task, not a variant of the HSBC/AMEX work.

## B-2 - the date pattern list is order-dependent and silently UK-biased

`parse_date` in `candidates.py` tries `("%Y-%m-%d", "%d/%m/%Y", "%d-%m-%Y", "%m/%d/%Y")`
and returns the first that parses. So `03/04/2026` is always 3 April, never 4 March, and
`%m/%d/%Y` is unreachable for any day <= 12 - it only ever fires on days 13-31.

A US-format export would therefore not fail cleanly: roughly half its rows would parse
**wrongly** and the rest correctly, which is worse than rejecting the file outright.
Day-first vs month-first cannot be recovered from the file; it has to be stated. Handle it
the way `amount_sign` is handled - an explicit answer, defaulted per source - never by
guessing.

## 1.2 The run order — cheapest signal first

Do them in this order and stop at the first that genuinely surprises you.

**A. AMEX CSV (the only format that currently commits)**

1. Import -> drop one AMEX CSV -> pick/create account `AMEX`.
2. Read the preview: does the row count match the statement? Dates right?
   Descriptions intact?
3. All AMEX amounts are unsigned positives, so the preview will ask for the sign
   convention before it lets you commit. Choose **Debit-positive (positive = charge)**.
   Every row should flip to an outflow and the commit button should unblock with
   "Ready to commit N transactions". If it stays blocked, read the reason it gives.

4. Then Overview / Activity: is that month's spending roughly what the statement says?

**B. HSBC current-account CSV** — expected to be blocked (headerless export;
`DictReader` eats row 1 as the header). Record the exact issue code shown.

**C. HSBC current-account PDF** and **D. AMEX PDF** — expect rows extracted but
0 valid, commit blocked. What matters is *which* rows are wrong: screenshot the
preview and note whether the failures are dates (`21 Jul 25`, `Jul31`), `CR`
markers, header detection, or junk lines promoted to candidates.

**E. HSBC credit-card PDF** — expect `PDF_NOT_EXTRACTABLE`. These are image-only;
they need OCR and `tesseract` is not on `PATH`. Install it or skip this case.

**F. Ask PFA** — ask one question you already know the answer to from the
statement. Ignore the "Zero Hallucination Guarantee" label; the facts panel is
currently a generic month summary, not the facts behind that specific answer.
That overclaim is still open and is not covered by any phase below yet.

## 1.3 What to write down

Per file: issuer, format, rows extracted, rows valid, blocking issue codes, one
screenshot of the preview. That table is the input to Phase 2 — each distinct
failure becomes a fixture.

# Part 2 — Decisions on the v0.2 proposal

**Agreed and adopted as written:** native-currency storage; reporting currency as
a separate concept; FX as its own dated snapshot with provenance; historical vs
current FX are different questions; investments in scope; holdings snapshot
before trade ledger; no real-time prices; manual prices as a first-class source;
scope stops at wealth tracking (no execution, no tax filing, no bank sync).

**Five changes to the proposal.**

### 1. The Money/Currency refactor is roughly 80% already done

`Money` already carries `currency` (`domain/money.py:12`) and already refuses
cross-currency arithmetic. `accounts`, `transactions` and `budgets` all already
have `currency` columns (`db/models.py:28,47,67`). This is not a domain rewrite.
Four things are actually missing:

- the hard reject at `ingestion/service.py:141` (`unsupported currency ... GBP only`)
- `base_currency` in `Settings`
- an FX table
- **analytics, which blindly sums `amount_minor` across every row regardless of
  currency** (`analytics/service.py:76-91,237-242`)

That last one is the whole risk. Today, adding an INR account silently produces
`5,000 + 400,000 = 405,000` of something. Everything else is plumbing.

### 2. No MarketDataProvider Protocol in v0.3, and no FxRateService class

An interface with one implementation is cost with no benefit. FX is a table plus
`rate_on(date, base, quote)` and `latest(base, quote)`. Prices are manual entry
plus one AMFI NAV fetch function. The Protocol appears the day a second real
provider does, and the call sites won't need to change when it does.

### 3. FX and NAV data: deterministic HTTP, not web search

The rule PFA already enforces is *the AI never owns arithmetic*. An FX rate is
arithmetic input, so a rate obtained through a model is unreproducible,
unauditable, and cannot be replayed for a historical question six months later.

Everything PFA actually needs is available from two fixed, free, keyless endpoints:

| Need | Source | Why it fits |
|---|---|---|
| GBP/INR daily rate, current and historical | Frankfurter (ECB daily reference rates) | No key, has a historical date-range endpoint, one deterministic URL |
| Indian MF NAV | AMFI daily NAV file | Published once daily after close, exactly PFA's refresh cadence |
| Anything uncovered | Manual entry | Always available, shown with source and price age |

That is a plain HTTP call, not a search. Both stay local-first: no model, no key,
no third party seeing your holdings beyond the fact that a rate was requested.
Every stored rate keeps `source` and `retrieved_at` regardless of origin.

### 4. On embedding web search while keeping inference local

Worth being precise about the trade, because "local model + web search" is not
automatically local:

- **Ollama web search is a hosted service.** The model runs on your machine, but
  the search executes on Ollama's servers and needs an ollama.com API key. The
  query leaves your machine. For a finance app that is a real change to the
  privacy posture, not a detail.
- **A genuinely local option exists** if search is wanted later: a self-hosted
  SearxNG instance (Docker, aggregates public engines, has a JSON API) called
  from a normal tool function. Inference local, search local, nothing hosted.
  It is still the open web, so it is still not a source of record.

Either way, the boundary should be the same one PFA already draws:

```text
search  ->  advisor narrative and context     (allowed, unverified, labelled)
search  ->  a stored FxRate or PriceSnapshot  (never)
```

Recommendation: skip search for v0.2 and v0.3 entirely — Frankfurter and AMFI
cover the data PFA needs deterministically. Revisit SearxNG later if the advisor
turns out to need context that isn't in the ledger. If you do want a rate from a
search path, it must land as a *suggested* value requiring manual confirmation,
never as an automatic write.

### 5. Reordering

"Do currency before continuing statement work" is right for the *narrow* currency
change and wrong for the full FX/valuation layer. Building a valuation layer on a
pipeline that currently imports **zero** real PDF statements is building on air.

So: narrow currency core -> make real statements import -> FX/valuation ->
investments.

## Extractor architecture: one pipeline, injected dialects

Decided before the PDF layout work starts, because writing four banks' quirks flat and
pulling them apart afterwards costs more than putting the seam in first.

**Not** a class per statement type. Per-issuer subclasses would duplicate the shared
pipeline (line assembly, continuation merging, plausibility gating, validation,
fingerprinting), and they would make issuer *detection* a hard prerequisite - turning an
unrecognised statement into a hard failure instead of a partial import you can review.
The formats also cross-cut the issuers: Barclays PDF is two-column but a Barclays CSV
would not be, and HSBC current and HSBC card share a date format but not a layout or a
sign convention. In a class tree that shared behaviour runs diagonally, which is exactly
where Template Method starts leaking and subclasses begin overriding `extract()` wholesale.

Instead: one `StatementExtractor`, never subclassed, taking a frozen `Dialect` record.

```python
@dataclass(frozen=True)
class Dialect:
    name: str = "generic"
    date_formats: tuple[str, ...] = ("%Y-%m-%d", "%d/%m/%Y", "%d-%m-%Y")
    assemble: Callable[[list[Word]], list[_RawRow]] = single_column
    credit_markers: tuple[str, ...] = ("CR",)
    default_sign: str | None = None  # None = ask the user


GENERIC = Dialect()
HSBC = replace(GENERIC, name="hsbc", date_formats=GENERIC.date_formats + ("%d %b %y",))
AMEX_CARD = replace(GENERIC, name="amex", date_formats=("%b%d",), default_sign="debit_positive")
BARCLAYCARD = replace(GENERIC, name="barclaycard", assemble=two_column)
```

Rules that make this hold up:

- **`GENERIC` stays a working default.** An unrecognised statement falls through to it
  rather than being refused. Detection improves results; it never gates them.
- **The dialect comes from the Account, not from sniffing the file.** The user knows their
  own accounts. Detection is a suggestion when adding an account, not a dependency.
- **A dialect is a good guess, not permission to guess silently.** Where a source is still
  ambiguous after the dialect applies - sign convention, date order - it must still be
  asked, through the mechanism that already works.
- **Most quirks need no dialect at all.** Nothing breaks if every statement is willing to
  parse `21 Jul 25`, handle a `CR` marker, or detect two columns geometrically. Only add a
  field to `Dialect` when two issuers genuinely need the same input read two different ways.

## Phase 1 — Currency in the core, narrow (1-2 days)

- [ ] `Settings.base_currency: str = "GBP"`
- [ ] Replace the GBP-only reject with an ISO-4217 check against a small
      `{code: minor_exponent}` dict (GBP 2, INR 2, USD 2, EUR 2, JPY 0). A dict,
      not a currency library.
- [ ] Candidate currency defaults from the **destination account**, not `"GBP"`
      (`extractors/csv.py:58`, `extractors/pdf.py:379`). Reject a commit whose
      candidate currency differs from the account currency.
- [ ] **Analytics becomes per-currency.** `monthly_summary`, category/merchant
      totals, cashflow and budget status all group by currency. No aggregate ever
      sums two currencies. Add a mixed GBP/INR fixture asserting exactly that —
      this is the one piece that must not be got wrong quietly.
- [ ] Migration `0003`: `fx_rates(base_currency, quote_currency, rate TEXT,
      effective_at DATE, source TEXT, retrieved_at DATETIME)`, unique on
      (base, quote, effective_at). Rate stored as a string and parsed to `Decimal` —
      SQLite has no decimal type and float rates are not acceptable here.
- [ ] `rate_on(date, base, quote)` — nearest rate **at or before** the date,
      never after — and `latest(base, quote)`.
- [ ] One conversion function, `to_base(Money, on_date) -> (Money, FxRate)`. The
      rate used is returned, never hidden. Nothing else in the codebase converts.
- [ ] `pfa fx set INR GBP 0.00863 --on 2026-08-29` and `pfa fx fetch` (Frankfurter).
- [ ] UI: currency shown per figure; consolidated totals labelled with the rate date.

**Deliberately not in Phase 1:** back-filling historical rates for existing data,
FX gain/loss reporting, multi-base reporting.

**Data-model requirement so v0.4 and later aren't blocked:** cost basis is stored
in its **cost currency**, and every FX rate applied to a valuation is recorded.
That is what makes local-asset return and FX return separable later without a
migration. Do not store a GBP-converted cost.
